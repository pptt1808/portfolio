01
ORIGIN

为什么做这个项目

先看见更多可能，
再决定自己想做什么。

我原本以为自己会沿着专业方向做开发。直到准备求职、接触实际项目和实习，我才逐渐确认，自己更喜欢梳理问题、理解需求，并和不同的人一起把产品做出来。

我想到了小时候的职业体验馆。

小时候去职业体验馆，常见的是警察、消防员、医生、教师。长大后，我们更可能进入产品、运营、HR、设计或测试等岗位。但这些工作的实际内容离学生阶段的生活有些远，很多人只有真正开始实习或求职，才有机会接触它们具体在做什么。

所以我想把一段具体的工作过程提前放到用户面前，让大家在真正进入公司之前，先有机会做一遍。

我想解决的一个具体问题如果能早点体验一次，选择时会不会少一点迷茫？

很多职业只有真正进入团队后，工作内容才会清楚起来。我想先给用户一段可以自己推进的任务，让他们在做的过程中了解这份工作，再决定要不要继续探索。

我的观察

有些工作离学生的日常生活，确实有一段距离

招聘描述能告诉你职责，却很难让你提前知道问题怎么出现、工作怎么推进，以及自己会不会从这个过程里获得成就感。

我的产品假设

先做一段具体任务，再想想自己喜不喜欢

产品不会替用户判断，只提供任务、工具和协作对象，让用户自己做决定、自己完成过程。

体验原则

给工具和提示，但不把流程做成选择题

模拟真实工作环境，AI 负责追问、整理和扮演协作对象，用户仍然要自己提出想法并推进方案。

02
SPACE

从工作台开始

把办公室里的工作，做成可以直接上手的体验。

这里没有课程，也不会直接告诉你“适不适合”。每个岗位都有自己的工作台、软件、协作对象和产物。你要从一封邮件开始，自己把任务往下推进。

领取任务→澄清问题→选择构思→形成方案→测试迭代→交付复盘
03
BRIEF

产品经理体验 · 领取任务

读懂一封没说清楚的邮件。

邮件里说，朋友们总在群里讨论周末去哪儿，却一直没有形成计划。它没有直接告诉你要做什么功能，你得先判断：问题到底出在哪里？

04
DISCOVER

澄清问题 · 选择构思

同一个现象，可以做成两种完全不同的产品。

Mentor 会追问你面对的是谁、问题发生在哪一步、第一版要解决什么。你怎么判断根因，后面的 PRD、流程、测试和原型都会跟着变化。

根因 · 信息不透明

把大家的共同点、冲突和需要放弃的东西放在一起看。

分别写下限制 → 汇总共同点和冲突 → 看清谁要妥协 → 接受 / 提出替代 / 否决并说明原因。

确认率 42%平均耗时 23 分钟v2 补充协商入口
根因 · 无人负责收敛

先把规则说清楚，再让一个人负责把计划定下来。

先定共同边界 → 轮值主理人接棒 → 发布计划 → 参加 / 本周跳过 / 边界否决 → 到期锁定。

主理人责任成员轻量响应换人和保底兜底

当前 Demo 先用两条预设案例展示：你怎么理解问题，会影响后面做什么。以后接入真实 AI，可以从用户自己的描述继续往下展开，而不是只提供两个固定选项。

05
BUILD

形成方案

把想法写下来，再做成可以点开的原型。

用户先在 Docs 里写 PRD，和 Mentor 来回修改几轮；再进入 Figma，把页面流程、Frame 和交互连接起来。AI 可以帮忙整理，但具体做什么、删什么，还是要用户自己决定。

06
TEST

测试迭代

做完不算结束，还要看看别人怎么用。

设计、开发、业务和模拟用户会从不同角度提出意见。20 组模拟测试材料显示，用户在哪一步犹豫、花了多久、最后有没有确认。用户再回到 Figma，把这些反馈改成下一版页面。

当前 AI 边界

固定案例 · 预设脚本 · 本地规则 · 结构化模板。 当前原型未接入真实生成式 AI；这些机制用于验证开放表达、角色协作与工作状态如何组织。真实 AI 是下一步能力，不在此伪装为已实现。

07
DELIVER

交付复盘

把一个模糊的问题，变成真正可以使用的产品。

最终留下的不只是 PRD 和原型，而是一个从问题判断开始、经过协作和验证，最后真的可以打开和体验的产品。对我来说，产品经理的成就感就在这里：把一个还说不清楚的问题，逐步变成别人可以使用的东西。

实现

React 18 / TypeScript / Vite / 原生 CSS

每条职业故事使用独立 LocalStorage key 保存软件位置、完成动作、对话进度与工作产物。

当前边界

没有后端、账号、云同步与真实多人协作

页面刷新后可继续体验，但固定内容仍直接存在前端组件中，职业案例尚未抽象为通用内容引擎。

产品方向

让用户从自己的想法继续往下做

接入真实 AI 后，可以根据用户的描述继续追问并生成协作反馈，同时补充内容安全、事实核验和职业专家审核。

08
HRBP

HRBP 体验 · 领取信号

HRBP 先做的，不是下结论，而是把线索查清楚。

CASE 07 从主管的一封邮件开始。你不能马上判断是能力、态度还是离职问题，而要先去看记录、找人聊、安排行动，再回来确认有没有变化。

09
CHECK

多方核对

先把不同来源的信息放在一起看。

WorkTime 里的调班和出勤、Talent 里的发展记录，以及 Mentor 和同事的观察，都只能说明一部分。你要先分清哪些事已经有记录，哪些还需要通过面谈了解。

10
MEET

员工面谈

一边听，一边记，也要决定下一步问什么。

先在 Docs 里准备目标、开场、问题、边界和回访安排。进入 Meet 后，小林会表达、犹豫，也会反问。用户要边听边记，再决定要不要追问，以及下一步怎么安排。

11
LOOP

行动回访

面谈之后，还要确认事情有没有真的发生。

面谈纪要只保留解决问题需要的信息：谁负责、什么时候做、排班怎么调整、发展反馈是什么。Tasks 负责跟进行动，DAY 14 再回到员工这里，确认承诺有没有变成实际变化。

12
DRIVE

HR 交付复盘

把面谈、行动和回访整理成一份工作记录。

最后留下的不是一份对员工的评价，而是面谈纪要、主管沟通、行动跟踪和员工回访。它记录已经确认的事实、谁负责什么，以及后面还要怎么验证，方便团队继续处理。

当前 AI 边界

固定案例 · 预设脚本 · 本地规则 · 结构化模板。 当前 HR 原型已实现真实工作空间与完整交互路径，但尚未接入真实生成式 AI、后端账号或多人协作。AI mentor、角色对话与自动归档仍是下一阶段产品方向。

13
NEXT

项目反思 · 下一步

它还是一个 Demo，但我觉得值得继续做。

现在的 Possibility OS 还是固定案例、预设脚本和本地规则，没有真正接入生成式 AI。我对产品经理和 HRBP 的理解也一定不完整，所以这里展示的不是岗位的完整定义，只是我目前想到的一种体验方式。

01 · 先说清楚边界

现在的它还不能代表真实岗位

角色不会真正理解用户，也不能无限生成分支。产品经理和 HRBP 的案例来自有限观察和个人建模，更多是一个可运行的 Demo。

02 · 我为什么还想做

我希望它能让人早点接触不同岗位

我自己原本以为会做开发，找工作和实习后才确认自己更想做产品。所以我希望大家不用等到最后一刻，才第一次接触这些工作的具体内容。

03 · 如果继续做下去

需要真实从业者参与

如果以后扩展到更多行业，案例、判断和细节都应该由真实从业者参与提供和审核，再由产品团队把它们做成可以体验的内容。

真实从业者提供案例→职业专家审核与校准→产品团队设计体验→AI 扩展互动可能→学习者实践与反馈

我不希望它替任何行业下定义。如果继续做下去，我更希望真实从业者把自己的工作带进来，一起把这些内容做得更接近实际。
