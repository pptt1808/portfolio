CityWalk Pulse · 产品案例

一个贯穿规划、行中、记录与分享的城市探索 Agent

CityWalk Pulse 让同一个 Agent 携带路线状态与真实事实，连接 Web 端规划、移动端执行、途中图文记录和结束后的内容表达；真实完成与反馈随后进入记忆，继续影响下一次规划。

产品阶段
可运行的高保真全栈原型
我的角色
个人主导产品探索与全栈原型
产品形态
Web + 原生 Android + Agent 后端

核心闭环

  1. 01表达感觉，生成路线
  2. 02执行路线，随时调整
  3. 03留下图文，整理记录
  4. 04选择表达风格，生成分享

01 · 机会

人们想要的不是更多景点，而是一段属于此刻的城市体验

CityWalk 以感受为目标、以真实空间为约束。用户说的是“轻松、有历史感、想慢慢逛”，产品要回答的却是：去哪、怎么串联、现在是否适合出发，以及计划改变后什么仍然成立。

01

模糊感受 × 精确行动

开放式审美不能被几个固定标签耗尽，但最终必须落到可导航的地点、距离与停留节奏。

02

理想路线 × 现场变化

下雨、疲惫或偏航会让静态计划失效；产品需要保留已经发生的旅程，只重算剩余部分。

03

一次建议 × 长期理解

生成、收藏与真实完成是不同强度的证据。记忆如果没有门槛，推荐会被自己的输出反向污染。

02 · 规划

把一句感觉，翻译成一条可以出发的路线

路线结果由一张可快速检查的决策界面组织：先看总览，再下钻每一站，最后交给地图核对空间事实。

“周六下午在上海，两位朋友从陕西南路地铁站出发，想看历史建筑、逛书店，中途安排一家室内咖啡馆休息，节奏轻松，控制在三小时内。”

一段自然表达同时包含地点、同行者、兴趣、节奏、休息方式与时间上限

第一层 · 决策总览

先让用户判断：这条路线现在能不能走

同一屏呈现城市、起终点、同行关系、交通与停留耗时、预算、天气风险和站点顺序。真实运行结果为 3 小时、预计 ¥106；70% 降雨风险触发室内优先与备选交通提醒。

第二层 · 逐站方案

每一站都说明为什么去、怎么去、要付出什么

Agent 将每一站展开为同一信息结构，避免推荐理由和执行信息彼此割裂。用户可以继续核对交通方式、距离、时间、推荐理由、风格标签、地址、评分、停留、费用、预约和来源。

  • 交通公交地铁 / 步行、分段距离与时间
  • 选择推荐理由、体验标签与风格匹配
  • 事实地址、评分、距起点距离与建议停留
  • 成本费用说明、预约条件与公开来源

第三层 · 事实校验

Agent 负责理解与排序，地图负责核对事实

模型可以理解开放式感受、编译搜索提示与解释排序，但地点名、坐标、地址、距离和路径必须回到地图。网页发现只作为线索，只有再次匹配到地图 POI 的候选才进入路线。

Agent

约束理解 · 候选排序 · 风格解释 · 冲突提示

地图

地点存在 · 坐标地址 · 空间顺序 · 分段距离

03 · 行中

真正的路线，从出发后才开始变化

行中体验同时处理两件事：路线随现场变化，旅程片段也能被快速留下。动态改路保障继续执行，随身记录为下一章提供图文、时间与位置。

动态改路

修改剩余旅程，不抹掉已经发生的旅程

  1. 锁定

    固定已完成站点、当前位置与既有轨迹

  2. 局部 Patch

    只替换剩余站点，继续继承同行者与硬约束

  3. 再核算

    更新距离、时长与预算，并保留撤销入口

随身记录

在最少操作里，留下此刻和位置

  • 拍照或上传多张图片
  • 输入一段当下文字
  • 自动关联当前位置或当前站点
  • 保存为沿途图钉
  • 完成后同步到 Web 记录

04 · 记录

把沿途片段，整理成一份可以继续编辑的城市记录

沿途图钉承接照片、文字、时间与位置。用户可以保留原始片段，也可以选择用 AI 重新表达某个场景，再按行走顺序整理为可翻阅、可继续编辑的记录。

01原始片段

照片、文字、时间与位置独立保存

02场景蒸馏

视觉分析与 Seedream 生成可选版本

03版本切换

原图与 AI 版本分层，文字仍可编辑

04沿路线成册

按图钉顺序组织为可翻阅跨页

05 · 分享

让一次真实漫步，拥有适合分享的表达

Agent 的 social_copy 能力把路线、沿途记录与用户想表达的语用编译成可发布的分享内容：先判断是实际分享、计划分享还是同行邀约，再输出同一表达风格下的完整版与简短版。路线事实和沿途记录会被分级为证据等级。

01

请求识别

先判断语用：实际分享、计划分享或同行邀约，再确定朋友圈、小红书、微博或 Caption 的表达任务。

02

证据编译

路线事实、用户片段与 Walk 记录分级进入；证据等级决定哪些细节可以写进文案。

03

语言指纹

把句式节奏、叙事推进、细节范围和结尾方式组合成稳定表达风格，而不是套用一个风格标签。

04

生成与验收

同一表达风格输出完整版与简短版，经过独立语义评审后再交给用户复制、编辑和发布。

06 · 记忆

让每一次真实行为，成为下一次规划的依据

记忆系统参考开源项目 Mem0 的 Extract + Reconcile 思路，并围绕 CityWalk 的行为证据强度重新设计。写入来源限定为用户明确表达和达到阈值的行为证据；Agent 生成内容的偏好证据权重为零。

Semantic

语义记忆

稳定画像、类别偏好、风格偏好与长期约束，例如偏爱独立书店、避开拥挤商业街。

Episodic

情景记忆

某次真实旅程中的明确体验，例如去过一家咖啡馆并认为太吵。

Procedural

程序记忆

用户与 Agent 协作时更习惯的规划方式，例如雨天室内优先、每段少走路。

01 · Extract抽取候选事实

只从用户明确表达或合格行为事件中提取。

02 · Reconcile比较现有记忆

产生 ADD / UPDATE / DELETE / NONE，并保留来源与置信度。

→
03 · Recall混合召回

关键词、向量余弦相似度与记忆置信度共同计分。

04 · Apply按优先级使用

本轮明确要求始终高于最近对话、长期记忆与默认值。

短期上下文

最近对话与长期记忆分开

同一 threadId 保存多轮上下文，解决“换一家”“预算不变”等指代；这些消息不会自动永久化。

底层召回

关键词 + 768 维向量

Embedding 默认生成 768 维向量，并与内容哈希一起写入 SQLite；召回融合语义相似度、关键词命中与置信度。

失败降级

缩小能力，不伪造确定性

Embedding 未配置或失败时自动降级到关键词召回，记忆读写不停止；SQLite 精确计算适配当前个人原型规模。

什么才有资格成为长期偏好

  1. 路线生成不写偏好

    只能证明用户提出过一次要求。

  2. 一次收藏保留兴趣事实

    但不直接推断长期喜欢。

  3. 一次完成证据仍不足

    可能只是当下场景的结果。

  4. 明确反馈或多次独立完成进入候选记忆

    多次一致行为先以较低置信度写入，用户纠正始终更高。

07 · 评测

把产品判断，写进可以持续回归的证据

路线“看起来合理”远远不够。配套评测系统把场景、工具调用、最终答案和 Agent Trace 组织成一套可以批量执行、比较结果与定位失败的质量闭环。评测样例也从路线规划持续扩展到技能、文案、行中与手账——每个新功能上线前，先有自己的回归样例。

50条规划场景

40 条主回归 + 10 条无障碍与稳定性专项

11项混合指标

基础与专属质量共同评判，0.6 硬门槛直接拦截

4 + 1 + 6三类裁判

确定性规则 + 统计算法 + LLM / 混合裁判

样例家族 · 不止路线规划

规划

路线规划场景

约束解析、亲子、无障碍、天气敏感、低预算与极端约束兜底，覆盖从出发到收尾的完整规划链路。

技能

技能效果对照

六个内置技能逐一跑「有无技能」对照实验：用伪地图与伪天气工具验证技能真的改变检索关键词、室内偏好与最终站点，而不是只改了提示词。

文案

社交分享文案

平台识别、已走 / 未走口吻、邀约检测与风格组合逐项断言；文案必须锚定路线事实，禁止营销腔和虚构天气、食物与偶遇。

行中

行中记录与调整

行走会话、行中改路线与行走记忆写回，覆盖"走起来之后"的链路，验证规划之外的第二现场。

手账

手账生成

排版、Zine 版式与旅程叙事的结构校验，保证分享产物在真实数据下稳定可读、不塌版。

稳定

稳定性与降级

LLM 重试与模型降级、长期记忆读写、移动端同步：异常路径也要有可预期的行为，而不是静默失败。

08 · 边界

项目边界与产品收获

当前阶段是能力闭环已经落到代码的个人项目，下一步围绕真实用户、移动端环境和生成质量展开验证。

已实现

可运行的高保真全栈原型

  • 多意图 Agent、约束账本与结构化路线
  • 地图 / 天气 / 公开内容发现与二次核验
  • 动态改路、跨端同步、途中记录、成册与分享文案
  • 三层记忆、混合召回与配套评测接口
仍需验证

仍需真实用户验证

  • 专属评分是否比地图默认排序更符合感受
  • 密集街区的到达判断与行中操作是否足够快
  • 场景蒸馏的稳定美感、成本与使用意愿
  • 记忆阈值会不会学得太慢或产生错误推断
数据与能力边界

当前原型的验证口径

  • 尚未产生线上 DAU、留存或商业转化数据
  • Android 仍需正式环境的发布构建与真机兼容验收
  • 不承诺场馆的实时库存或预约余量
  • 评测结论只对应明确样本、指标与版本

我对 Agent 的理解，从“让模型输出更像答案”，转向了“设计状态、工具、证据、反馈与失败边界，让系统在多轮和真实世界变化中仍然可靠”。
